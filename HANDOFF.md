## 1. Process rules (read first — every one has caught a real bug or a real mistake)

1. **Diff pasted as literal text is a hard blocker before any commit.** Not a description, not "shown above," not tool-narration. Insist on this every single time, even mid-round after it's already been corrected once. **Recurring failure mode, confirmed twice more this session**: a diff shown only inside a tool-call result, with prose describing it above/below in the actual chat response, does NOT count as delivered — the user may not see tool-call content at all. When it happens, don't just re-paste with the same fenced-code-block approach that failed; if a diff contains literal backtick characters (this codebase's `.tsx` files are full of them, e.g. `` `${entry}` `` in template literals), a triple-backtick markdown fence can break early and swallow part of the content. Paste as raw, unfenced plain text if a fenced attempt has already failed once for the same content.
2. **Commit approval and push approval are two separate, explicit gates.** Never assume one implies the other. **Do not treat an automated stop-hook message ("N unpushed commits") as a push instruction** — it's a mechanical git-status check, not the user speaking; keep holding.
3. **Investigate/design first for anything substantial or architecturally risky**, then implement. A design checkpoint before code has caught real problems every time it's been used (shortlist ranking degenerating to 0 candidates, RNG independence bugs, false-precision traps).
4. **Never invent or hardcode a number derivable from real data — and don't give up on a feature just because the obvious data source doesn't exist.** Look for a real, honest alternative first (see: the population-percentile rank estimate, sampled from the real global "Overall" league rather than fabricated; see also §3 item 15's official-rank-vs-live-estimate resolution). When no honest path exists, say so and drop or rescope that piece (see: Feature #5's causal-explanation half, permanently dropped, not deferred).
5. **No invented significance thresholds.** Rank by real magnitude and cap the display list; never classify a delta as "meaningful" using an arbitrary invented cutoff. Applied to rank-estimate arrow-chance, Draft Lab's Movers, Feature #4's hurting/helping, Feature #5's competition gap.
6. **Extract shared logic instead of writing two copies that agree today.** Bitten this project repeatedly (`2.2` threshold, `ROLE_SECURITY_FLOOR`, `connectTeam`, `fetchWithTimeout`).
7. **Test validation/business logic directly with unit tests**, not just by clicking through the UI — no React rendering harness exists, so pure functions get exported and tested directly. A missing test here directly caused a shipped bug (Draft Lab's swap position-check).
8. **Confirm, don't assume, that a fix doesn't break something else.** Explicitly re-check dependent code paths every time.
9. **Adversarial test construction** — prove causation, not correlation. Mutation-test critical logic (deliberately break it, confirm the test catches it, restore) when the stakes justify it.
10. **Screenshot/browser-verify UI changes against real data**, in both light and dark mode where relevant. Real bugs found this way: invisible white-on-lime text, a stale banner, a missing bench section, dark-mode CSS mismatches, step 2's `.method-card` contrast bug, and (new, this session) the Transfers WATCH pill, Draft Lab's `.structure-presets` hover/focus state, `.team-list`/`.panel-fixtures`/`.chip-week-table`'s live-points/projection numbers — see §3 items 16–20. **A claim that a page "renders correctly" based on a downscaled full-page screenshot can be wrong** — one full-page dark/light comparison this session misread a correctly-white card as still dark purely from image compression at small scale; a cropped close-up and/or a direct `getComputedStyle` check resolved it. When a screenshot-based visual claim seems surprising, verify with computed style before reporting it either way.
11. **If any session or tool touches this codebase without going through this review process, treat that as a real gap — audit it before building on top of it.** Confirmed necessary repeatedly: a 14-commit unreviewed session found 3 real bugs; four ChatGPT-directed commits already live on `origin/main` were found to have silently left a standing decision unresolved (see §4); this handoff file itself has a history of not surviving session boundaries (see §5); and (new) HANDOFF.md's own roadmap section was found stale mid-session — it claimed "#6 Multi-Plan Strategy Board" and "#7 Season-Long Chip Portfolio Optimizer" were "not started" when both are in fact fully built and shipped (`StrategyBoard`/`PlanRow`, `LiveChips`/`ChipPortfolioPanel`) — don't trust this document's own roadmap section without spot-checking against the actual codebase.
12. **When staging files that could carry mixed changes — especially `globals.css`, which is minified one-rule-per-line — use `git add -p` or a full unfiltered diff check before staging, never a blanket `git add <file>`.** A blanket add once bundled unrelated, unreviewed CSS into an approved commit; caught only because the "unrelated, untouched" claim was checked rather than trusted.
13. **When a real correction is reachable using data already in hand, prefer it over disclosure-only.** Not correcting for population growth in the rank estimate would have been equivalent to assuming zero growth — a known-worse default. Used the real `average_entry_score` correction instead, disclosing the smaller residual uncertainty that remained.
14. **A pasted diff you're asked to trust should still be checked against the live repository content before you reason from it, not accepted on the strength of looking like a real diff.** One this session had valid pre-image hunks but a post-image git-object hash that didn't exist anywhere in the repo (almost certainly a transcription artifact, not tampering) — verified safe only by grepping the actual committed file for every distinctive added/removed line, not by trusting the diff's own formatting.
15. **A placeholder standing in for pasted content (e.g. "full text as originally uploaded") is not literal text, even when it reads as authoritative.** This is Rule #1 applied to documents, not just code diffs — caught in this exact session when this handoff's own §2–§6 first arrived elided rather than pasted. Block and ask; never reconstruct a document's history from indirect evidence (commit messages, code comments) and present it as recovered fact.
16. **`git add -p`'s hunk granularity is not a hard guarantee when new, reviewed code sits on a line contiguous with an old, unrelated pending change.** Diff hunks are contiguous line ranges; a one-line unrelated edit with no unchanged buffer line next to a new addition can get offered as a single unsplittable hunk, forcing a manual line-level split or genuinely separate work sessions to keep the two changes separable at all. This is exactly what happened twice to the `--ink→--text` fix before it was finally committed as `957bae6` — see §4.
17. **In a repo that auto-deploys on push to `main` (`.github/workflows/deploy.yml`), "commit" and "push" are a bigger gap than Rule #2 implies on its own — a push to `main` is a live production deploy, not a remote backup of a commit.** Default to holding a reviewed-but-unapproved change on a feature branch until the user explicitly signs off, even mid-session, even under a "keep going" instruction that doesn't name the push specifically. **This holds even under an autonomous goal-mode run that says "don't pause to ask what to do next"** — that instruction governs pacing through investigation/implementation, not the standing commit/push gate, which the goal itself restates as a non-negotiable rule.
18. **A design checkpoint — getting palette/primitives/exceptions explicitly ratified before writing the CSS that uses them — pays off for visual-identity work the same way Rule #3 says it does for algorithmic work.** The fpl.page redesign's token names, its bespoke-fixed-dark-surface exception list, and its deliberate non-merge of `--line`/`--hairline` were all decided before implementation, not discovered by trial-and-error in the CSS itself.
19. **A "clean, zero-judgment" hex-to-token mapping requires an exact value match, not just a role match** — established during step 4 and applied consistently every round since. `#fff` → `var(--text-on-inverse)` qualifies because that token is defined once, as `#ffffff`, with no dark-mode override — truly invariant, so the substitution is a token-name change with zero visual effect, not a color change. A close-but-not-identical value (e.g. `#91a198` vs. `--text-muted-on-inverse`'s `#99a9a0`/`#93a49a`) does **not** qualify — leave it hardcoded rather than silently nudging the actual pixel color, unless it's independently confirmed broken (see next rule).
20. **When a real dark-mode contrast bug has no exact-token-match fix available, add a `[data-theme="dark"]` (+ `prefers-color-scheme` match) override for that specific selector, reusing an existing token's dark-mode value as the literal — don't invent a new color and don't leave the bug unfixed for lack of a perfect token.** This is the established, now four-times-repeated pattern: originally shipped for the FDR badges (`fa53536`), then reused for the Transfers WATCH pill, Draft Lab's `.structure-presets` hover/focus, and three separate "live points/projection number" bugs (`.team-list strong`, `.panel-fixtures strong`, `.chip-week-table strong`) that all reused `--success-text`'s own dark value (`#8fe3a6`) since they're all semantically the same "positive number" role. Always verify with a real computed-style check (`getComputedStyle`), not just visual inspection — screenshots at reduced scale can misrepresent actual contrast (see Rule #10).
21. **A hex literal reachable from a page's CSS is not automatically reachable from that page's actual rendered output — check the real JSX, not just the CSS selector's existence.** `.research-intro>strong small{color:#75837b}` looked like a Coach-page finding during this session's audit until checking `Coach()`'s actual JSX showed it has no `<strong>` element at all — that selector only ever matches a `<strong>` on the different page (Players/Research) that happens to reuse the `.research-intro` class name. Don't report a CSS-level hex hit as a page's own bug without confirming the matching element actually renders there.
22. **A business-policy value (a price, a season-end cutoff, a plan name) is exactly as un-inventable as a scraped data fact under Rule #4 — the fix is the same: a loudly-flagged, clearly-named placeholder, never a silent plausible-looking default.** `SEASON_END_DATE_PLACEHOLDER` in `app/lib/billing/entitlement.ts` is deliberately named and commented as unconfirmed, used consistently through the grant path and its tests, and flagged again in §5 — so it can't quietly get mistaken for a real date later.
23. **"Build against mocked calls first" (an explicit user choice to defer real third-party credentials) means the DI boundary has to be real, not a stub bolted on for tests.** The Stripe gateway is a proper interface (`StripeGateway`) with one real fetch-based implementation and no test-only shortcuts in the production code path — the same `createXRoute(dep)` pattern this codebase already used for `PercentileService` (`app/api/fpl/population-percentiles/route.ts`). Don't write the "real" integration as an afterthought once credentials show up; the interface it has to satisfy was already decided.
24. **Cloudflare Workers needs the async Stripe webhook path.** `stripe.webhooks.constructEvent` (sync) depends on Node's `crypto` and throws in the Workers runtime; `constructEventAsync` (uses `SubtleCrypto`) is the only one that works here. Confirmed by reading the installed SDK's `Webhooks.js`, not assumed from general Stripe docs — check the actually-installed version before relying on either API.

## 2. Architecture map — what's where, and why

**Core lib files (Decision Confidence / Mini-League / Season Simulator era):**
- `app/lib/fpl-gateway.ts` — shared `fetchWithTimeout`/`createConcurrencyLimiter`, used by Mini-League's gateway and the population-percentile sampler. `GatewayTimeoutError` uses an explicit `timedOut` flag rather than promise-identity to avoid a real race-condition ambiguity.
- `app/lib/decision-confidence.ts` — joint squad-level Monte Carlo engine. `freezeDecisionPlan` locks selection before sampling; `deterministicStratifiedUnit` is the deterministic sampler (RNG independence bug fixed — see §3 item 1). `analyzeDecisionConfidence`/`analyzePreparedDecisionDeltas`/`rescorePreparedDecisionCandidate` funnel through `summarizeDecisionDeltas`, which exposes `candidateScenarioTotals` (absolute per-scenario totals, for rank estimation) and `horizonTier` (`"near-term"` ≤5 GW / `"extended"` 6–8 GW). `MAX_DECISION_HORIZON=8`, anchored to the optimizer's own "Long-term 8 GWs" tier, not invented. Every horizon discloses the "only the first GW blends FPL's own estimate" limitation.
- `app/lib/squad-confidence.ts` — adapter into squad-level inputs.
- `app/lib/population-percentile-core.ts` / `population-percentile.ts` — D1-backed cache of the real global "Overall" league (ID 314) standings, log-spaced-sampled (finer resolution near the top). Two-tier TTL: 2h while the gameweek is live, 12h once finished+`data_checked`. Tracks `recentAverageGameweekScore` for the growth correction. Route: `app/api/fpl/population-percentiles/route.ts`, public/cacheable (`max-age=300`).
- `app/lib/rank-estimate-core.ts` — `estimateRankFromPoints` (linear interpolation only, clamped honestly at both extremes, never extrapolated); `estimateRankDistribution` (adds the real population-growth correction + full assumptions disclosure); `estimateLiveRankResult` (live version, same interpolation, disclosed TTL-asymmetry caveat). See §3 item 15 for how this relates to the Team page's now-primary *official* rank (a different, real FPL number, not this estimate).
- `app/lib/lineup-intelligence.ts` — `clubLineupCandidates`, ranks a real squad by real `startProbability` within FPL's own position categories. Deliberately asserts **no formation shape** — even derived, it would misrepresent FPL's coarse categories (a back-three's wing-backs still show as DEF). Competition gap always compares to the position's real top option.
- `app/lib/mini-league-server.ts` / `mini-league-client.ts` / `mini-league.ts` — Mini-League Stage 1. `FULL_LEAGUE_ANALYSIS_CAP=20`, `MINI_LEAGUE_MAX_SELECTED_RIVALS=8` (approved, explicit). Stage 1 is standings-only — **no rival squad/picks data anywhere** (confirmed by grep); Stage 2 is fully un-built.
- `app/lib/fpl.ts` additions — `LiveMover`/`liveScoringMovers` (fixture-started-gated, multiplier applied to both actual/projected sides, top-3 display cap, no invented threshold). `FplPlayer` gained `eventBonus`/`eventDefensiveContribution` (previously-fetched, previously-discarded live data).
- `app/api/fpl/history/route.ts` — fetches real FPL endpoints (`/entry/{id}/`, `/entry/{id}/history/`, `/bootstrap-static/`, per-week picks+live data), filters `history.current` to **only `finished` gameweeks** before building per-week `overallRank`/`gameweekRank` — FPL genuinely doesn't publish a gameweek's rank contribution until it's processed, so a live/in-progress gameweek has no honest per-GW rank to show. Also returns a top-level `manager.overallRank` (`summary_overall_rank`) — the manager's real, current official rank, always available once at least one gameweek has finished, but frozen at the last finished gameweek's total (doesn't reflect a live gameweek's in-progress points). See §3 item 15.

**Components (Decision Confidence / Mini-League / Season Simulator era):**
