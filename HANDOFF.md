## 1. Process rules (read first — every one has caught a real bug or a real mistake)

1. **Diff pasted as literal text is a hard blocker before any commit.** Not a description, not "shown above," not tool-narration. Insist on this every single time, even mid-round after it's already been corrected once.
2. **Commit approval and push approval are two separate, explicit gates.** Never assume one implies the other.
3. **Investigate/design first for anything substantial or architecturally risky**, then implement. A design checkpoint before code has caught real problems every time it's been used (shortlist ranking degenerating to 0 candidates, RNG independence bugs, false-precision traps).
4. **Never invent or hardcode a number derivable from real data — and don't give up on a feature just because the obvious data source doesn't exist.** Look for a real, honest alternative first (see: the population-percentile rank estimate, sampled from the real global "Overall" league rather than fabricated). When no honest path exists, say so and drop or rescope that piece (see: Feature #5's causal-explanation half, permanently dropped, not deferred).
5. **No invented significance thresholds.** Rank by real magnitude and cap the display list; never classify a delta as "meaningful" using an arbitrary invented cutoff. Applied to rank-estimate arrow-chance, Draft Lab's Movers, Feature #4's hurting/helping, Feature #5's competition gap.
6. **Extract shared logic instead of writing two copies that agree today.** Bitten this project repeatedly (`2.2` threshold, `ROLE_SECURITY_FLOOR`, `connectTeam`, `fetchWithTimeout`).
7. **Test validation/business logic directly with unit tests**, not just by clicking through the UI — no React rendering harness exists, so pure functions get exported and tested directly. A missing test here directly caused a shipped bug (Draft Lab's swap position-check).
8. **Confirm, don't assume, that a fix doesn't break something else.** Explicitly re-check dependent code paths every time.
9. **Adversarial test construction** — prove causation, not correlation. Mutation-test critical logic (deliberately break it, confirm the test catches it, restore) when the stakes justify it.
10. **Screenshot/browser-verify UI changes against real data**, in both light and dark mode where relevant. Real bugs found this way: invisible white-on-lime text, a stale banner, a missing bench section, dark-mode CSS mismatches, and (new) step 2's `.method-card` contrast bug — see §3.
11. **If any session or tool touches this codebase without going through this review process, treat that as a real gap — audit it before building on top of it.** Confirmed necessary repeatedly: a 14-commit unreviewed session found 3 real bugs; four ChatGPT-directed commits already live on `origin/main` were found to have silently left a standing decision unresolved (see §4); this very handoff file has never been committed to the repo across its entire history, which is the same category of gap (see §5).
12. **When staging files that could carry mixed changes — especially `globals.css`, which is minified one-rule-per-line — use `git add -p` or a full unfiltered diff check before staging, never a blanket `git add <file>`.** A blanket add once bundled unrelated, unreviewed CSS into an approved commit; caught only because the "unrelated, untouched" claim was checked rather than trusted.
13. **When a real correction is reachable using data already in hand, prefer it over disclosure-only.** Not correcting for population growth in the rank estimate would have been equivalent to assuming zero growth — a known-worse default. Used the real `average_entry_score` correction instead, disclosing the smaller residual uncertainty that remained.
14. **A pasted diff you're asked to trust should still be checked against the live repository content before you reason from it, not accepted on the strength of looking like a real diff.** One this session had valid pre-image hunks but a post-image git-object hash that didn't exist anywhere in the repo (almost certainly a transcription artifact, not tampering) — verified safe only by grepping the actual committed file for every distinctive added/removed line, not by trusting the diff's own formatting.
15. **A placeholder standing in for pasted content (e.g. "full text as originally uploaded") is not literal text, even when it reads as authoritative.** This is Rule #1 applied to documents, not just code diffs — caught in this exact session when this handoff's own §2–§6 first arrived elided rather than pasted. Block and ask; never reconstruct a document's history from indirect evidence (commit messages, code comments) and present it as recovered fact.
16. **`git add -p`'s hunk granularity is not a hard guarantee when new, reviewed code sits on a line contiguous with an old, unrelated pending change.** Diff hunks are contiguous line ranges; a one-line unrelated edit with no unchanged buffer line next to a new addition can get offered as a single unsplittable hunk, forcing a manual line-level split or genuinely separate work sessions to keep the two changes separable at all. This is exactly what happened twice to the `--ink→--text` fix before it was finally committed as `957bae6` — see §4.
17. **In a repo that auto-deploys on push to `main` (`.github/workflows/deploy.yml`), "commit" and "push" are a bigger gap than Rule #2 implies on its own — a push to `main` is a live production deploy, not a remote backup of a commit.** Default to holding a reviewed-but-unapproved change on a feature branch until the user explicitly signs off, even mid-session, even under a "keep going" instruction that doesn't name the push specifically.
18. **A design checkpoint — getting palette/primitives/exceptions explicitly ratified before writing the CSS that uses them — pays off for visual-identity work the same way Rule #3 says it does for algorithmic work.** The fpl.page redesign's token names, its bespoke-fixed-dark-surface exception list, and its deliberate non-merge of `--line`/`--hairline` were all decided before implementation, not discovered by trial-and-error in the CSS itself. Do the same before steps 4–5.

## 2. Architecture map — what's where, and why

**Core lib files (Decision Confidence / Mini-League / Season Simulator era):**
- `app/lib/fpl-gateway.ts` — shared `fetchWithTimeout`/`createConcurrencyLimiter`, used by Mini-League's gateway and the population-percentile sampler. `GatewayTimeoutError` uses an explicit `timedOut` flag rather than promise-identity to avoid a real race-condition ambiguity.
- `app/lib/decision-confidence.ts` — joint squad-level Monte Carlo engine. `freezeDecisionPlan` locks selection before sampling; `deterministicStratifiedUnit` is the deterministic sampler (RNG independence bug fixed — see §3 item 1). `analyzeDecisionConfidence`/`analyzePreparedDecisionDeltas`/`rescorePreparedDecisionCandidate` funnel through `summarizeDecisionDeltas`, which exposes `candidateScenarioTotals` (absolute per-scenario totals, for rank estimation) and `horizonTier` (`"near-term"` ≤5 GW / `"extended"` 6–8 GW). `MAX_DECISION_HORIZON=8`, anchored to the optimizer's own "Long-term 8 GWs" tier, not invented. Every horizon discloses the "only the first GW blends FPL's own estimate" limitation.
- `app/lib/squad-confidence.ts` — adapter into squad-level inputs.
- `app/lib/population-percentile-core.ts` / `population-percentile.ts` — D1-backed cache of the real global "Overall" league (ID 314) standings, log-spaced-sampled (finer resolution near the top). Two-tier TTL: 2h while the gameweek is live, 12h once finished+`data_checked`. Tracks `recentAverageGameweekScore` for the growth correction. Route: `app/api/fpl/population-percentiles/route.ts`, public/cacheable (`max-age=300`).
- `app/lib/rank-estimate-core.ts` — `estimateRankFromPoints` (linear interpolation only, clamped honestly at both extremes, never extrapolated); `estimateRankDistribution` (adds the real population-growth correction + full assumptions disclosure); `estimateLiveRankResult` (live version, same interpolation, disclosed TTL-asymmetry caveat).
- `app/lib/lineup-intelligence.ts` — `clubLineupCandidates`, ranks a real squad by real `startProbability` within FPL's own position categories. Deliberately asserts **no formation shape** — even derived, it would misrepresent FPL's coarse categories (a back-three's wing-backs still show as DEF). Competition gap always compares to the position's real top option.
- `app/lib/mini-league-server.ts` / `mini-league-client.ts` / `mini-league.ts` — Mini-League Stage 1. `FULL_LEAGUE_ANALYSIS_CAP=20`, `MINI_LEAGUE_MAX_SELECTED_RIVALS=8` (approved, explicit). ## 4. Standing decisions and traps worth knowing

- **`confidenceMultiplier` in `transfers.ts` stays, deliberately**, as the only affordable full-sweep ranking heuristic — the Decision Confidence Engine is a different, opt-in, too-expensive-to-run-per-candidate tool. Don't "finish the job" by removing it without a cheap replacement.
- **`MAX_DECISION_HORIZON=8`** is anchored to the optimizer's existing tier, not a fresh number — no principled cliff between GW6/GW7, so don't invent a different cutoff later without the same reasoning.
- **No invented significance thresholds anywhere** (rank/arrow-chance/movers/lineup-competition) — rank by real magnitude, cap the list, let the reader interpret.
- **The population-percentile curve is a ~29-point real sample**, log-spaced, on a 2h/12h TTL, reflecting *today's* leaderboard shape. The growth correction is a real but imperfect estimate; its residual uncertainty is disclosed everywhere the curve is used — don't quietly drop that disclosure in a future surface.
- **Mini-League Stage 1 has zero rival squad/picks data.** Anything implying "vs. what your rivals are doing" beyond raw global % is blocked on Stage 2, not partially built.
- **`/api/fpl`'s server-side edge cache floors real freshness around 5 minutes**, regardless of client polling. Tightening it is a separate, app-wide, explicitly-scoped future item, not a silent bundle into a feature.
- **Formation/tactical-shape claims are permanently declined**, even derived — FPL's own position categories are too coarse to support them honestly.
- **Never trust a diff-review round's own "unrelated, untouched" claim about a file without checking.** It was wrong once (the footer CSS), caught only because it was asked to be shown anyway.
- **Two token systems coexist in `globals.css` on purpose.** Don't merge `--line`/`--hairline` or `--paper`/`--canvas` without re-deriving whether that's actually safe — they were kept separate deliberately in step 1 and that reasoning hasn't been revisited since.
- **`--ink`/`--lime`/`--wline` are real, load-bearing tokens outside marketing** — confirmed the hard way in step 2 after step 1 assumed otherwise. Don't repeat that assumption for any token not explicitly documented as marketing-only.
- **Bespoke fixed-dark surface is now a named, reusable category**: `hero-product`, `brand-mark`, `confidence-ring` (step 2), `coach-sidebar`, `coach-mobile-nav`/`mobile-more` (step 3) all stay `--canvas-dark`/`--canvas-light` regardless of app theme — a permanent nav column or a literal/identity element shouldn't flip with theme. Use this category for the next such surface instead of re-litigating the exception from scratch.
- **The `--ink`→`--text` fix has an unusual history, now resolved — recording it precisely rather than dropping it, since the path here is a real lesson.** The change is to `.hero h1 em`, `.section h2 em`, and `footer h2 em` in `app/globals.css`: `--ink` has no dark-mode override (defined exactly once in the whole file) while the actual background (`--paper`) is theme-reactive, so in dark mode the stroke was near-invisible against it. It originated *before* the UI overhaul, survived two absorption near-misses during steps 1–2 (a `git add -p` hunk-granularity close call, then a deliberate revert-then-restore around step 2's commit, both documented in those commits' own messages) — and then, critically, **the uncommitted diff itself did not survive a session boundary**: the session that carried it forward never committed it, and once that session's container was gone, so was the diff, with no trace in git (confirmed: empty `git diff`/`git stash list`, clean `git reflog`). It was only recovered because a **separate, parallel conversation** against this same repo had independently diagnosed and approved the identical fix that same day and still had the literal diff text in its own history — recovered from there, re-verified independently in this session (grepped the actual token values fresh, didn't take the parallel session's diagnosis on trust), confirmed real by fetching `origin/main` and finding the bug still live there. **Fixed and committed here as `957bae6`**, screenshot-verified both modes, held out of the push same as everything else. The lesson: an uncommitted fix is not "pending," it's unsaved — the moment a session ends without a commit, it can be gone for good regardless of how many times it was correctly diagnosed.
- **The Cloudflare deploy pipeline (`.github/workflows/deploy.yml`, added mid-session as `2e174ba`) makes push-to-`main` a real, live production deploy.** Step 3 is intentionally sitting on a feature branch pending explicit approval — see Rule #17. Don't push to `main` on behalf of a "keep going" instruction that doesn't name the push specifically.
